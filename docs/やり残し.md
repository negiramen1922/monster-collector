**なぜこの数字なのか（測って分かったこと）**

- 旧のタンクは1戦で **手番の40%が回ってこない**（1ウェーブ2.1ラウンドで終わり、遅い子の順番が来る前にウェーブが終わる）。
- 旧のSP収支はタイタンで「行動38＋被弾33＋撃破4＝76」、必要SP120。**構造的に届かない**。
- 被弾SPを「自分の最大HPの%」にすると、HPの多いタンクほど損をする。→ **平均HP基準**にした。
- SP獲得を一律で増やすと、アタッカーだけ伸びて戦闘が短くなり、**タンクの手番がさらに減る**（自滅ループ）。一律は不可。
- 奥義の必要SPを一律で下げても同じ理由でタンクは悪化する（0.34→0.11）。**ロール別でないと意味がない**。
- 防御を割合式（`raw×(1−def/(def+raw×K))`）にしても何も変わらない。後衛の防御値は敵の攻撃に対して元々小さく、軽減率はタンク39% / 後衛4〜5%のまま。**後衛が溶ける問題はHPで解くのが正解**（1発の被ダメが最大HP比 67% → 40%）。
- シールドは旧だと**付与の85%が上限で切り捨て**られ、実際に付くのは要求の75%だった。

  「防御も×2」か「防御を割合式」を測り直すこと（v1では割合式に効果がなかったが、v2では話が変わる）。

  甘いステージを締めると q5_08 が 5〜27% まで落ちる。**実際に遊んでから、詰まる/緩いステージを

### 1-1. タンクとサポーターの奥義が撃てない  ※α0.3.000 で対応ずみ（1-0 を見ること）

## 2-7. フォロワーが出ない（調査中）

α0.2.007 で次を入れた。
- 取得に失敗しても黙って空にせず、画面に理由を出して**再読み込み**できるようにした。
- 「フォロワーは◯人います」と出ているのに一覧が空、という見分けのつかない状態をなくした（何人ぶん読めたかを出す）。
- `syncFollowRecords()` が「1セッション1回」で、ログイン直後のフレンド未読み込みのときに空振りで終わっていたのを、顔ぶれが変わったら書き直す形にした。

### いちばん怪しいところ：Firestore のルールが反映されていない

`players/{uid}/incoming`（誰が自分を追加したかの記録）は、`players/{uid}` とは**別のルール**が要る。
Firestore のルールは親から子へ引き継がれないので、`incoming` のぶんが無いと**読み書きの両方が拒否**され、フォロワーはいつまでも0になる。

このルールが `firestore.rules` に入ったのは **2026-09-22 のコミット `d04fb42`**。
`firestore.rules` はリポジトリに置いてあるだけで自動では反映されないので、**そのとき反映していなければ今も古いまま**。

```bash
firebase deploy --only firestore:rules
```

または Firebase コンソール → Firestore Database → ルール に `firestore.rules` の中身を貼り付ける。
コンソールの「ルール」画面に `match /incoming/{fromUid}` の行があるかどうかで、反映済みか一目で分かる。

**それでも出ない場合**、フォロワー画面に何と出ているかで切り分けられる。

| 画面の文言 | 意味 |
|---|---|
| フォロワーの一覧を**読む権限がありません** | **ルールが古い**（上の deploy をする） |
| フォロワーの一覧を取れませんでした | `players/{自分}/incoming` が読めていない（通信かルール） |
| フォロワーのプロフィールを取れませんでした | `incoming` は読めたが `players` の一括取得が失敗 |
| ◯人のうち△人のプロフィールが読めませんでした | 相手の `players/{uid}` が無い |
| まだフォロワーがいません（フォロワー数も0） | `players/{自分}/incoming` が空。相手側の書き込みが届いていない |

最後のケースなら、**相手が自分を追加したときに `recordIncomingFriend` が走っているか**を疑う。
`addFriendByCode` と `syncFollowRecords` の2か所から書いている。
