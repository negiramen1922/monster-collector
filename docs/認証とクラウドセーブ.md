# 認証・アカウント・クラウドセーブ

対象: `index.html` の「account, sign-in and cloud save」「title screen」「account panel」セクション

---

## 1. プレイヤーから見た流れ

1. ゲームを開くと**タイトル画面**が出ます。前回ログインしている人はここを素通りして、そのままゲームが始まります。
2. はじめての人は3つから選びます。
   - **Googleでログイン** … ポップアップ。ブロックされた場合はリダイレクトに切り替わります。
   - **メールアドレスで始める** … ログイン/新規登録、パスワード再設定つき。
   - **ゲストで遊ぶ** … Firebaseの匿名ログイン。あとからGoogle・メールに引き継げます。
3. ログインすると**プレイヤーID**(例 `86RH-4EED-PMHK`)が割り振られます。ホーム画面下のアカウント欄から、ID確認・コピー・名前変更・引き継ぎ・ログアウトができます。
4. セーブはこの端末とクラウドの両方に入り、**別の端末で同じアカウントに入ると続きから**遊べます。

## 2. Firebase側の設定

| 項目 | 内容 |
|---|---|
| プロジェクト | `monster-collector-80b5b` (設定値は `index.html` の `FIREBASE_CONFIG`) |
| Authentication | Google / メール・パスワード / 匿名 を有効化 |
| 承認済みドメイン | 配信先のドメインを Authentication → Settings → 承認済みドメイン に追加。**ここに無いとGoogleログインが失敗します** |
| Firestore | ルールはリポジトリの `firestore.rules`。コンソールに貼るか `firebase deploy --only firestore:rules` |

- `apiKey` は秘密の値ではありません(プロジェクトを指すIDで、それ自体では何もできません)。データを守るのは**Firestoreのルール**です。
- **`file://` で直接開くとログインできません**(FirebaseのSDKもFirestoreもHTTP配信が前提)。ローカルで試すときは `python3 -m http.server` などを使ってください。

## 3. Firestoreのデータ構造

```
players/{uid}         公開プロフィール  { playerId, name, provider, monsters, cleared, updatedAt }
players/{uid}/gifts/{giftId}  フレンドポイントの受け取り箱  { from, amount, at }
saves/{uid}           セーブ本体        { savedAt, version, data }   data はSTATEのJSON文字列
playerIds/{code}      フレンドコード表  { uid, at }
```

- `saves` は本人だけが読み書き、`players` はログイン済みなら誰でも読めます(フレンド一覧・PVPの相手表示用)。
- `playerIds` は `code → uid` の逆引き。作成のみ許可で、他人のコードは奪えません。
- `players/{uid}/gifts` はフレンドへのポイント送信(`sendFriendPoint`)が相手のuid宛てに作成する、他人のドキュメントに書き込める唯一の経路です。送信者は自分のuidしか名乗れず(`from == request.auth.uid`)、金額も`FRIEND_POINT_PER_SEND`(10)固定なので任意の値を送りつける穴にはなりません。受け取った本人だけが読める/消せて、`claimFriendGifts`がログイン時とフレンド一覧を開いた時に回収し、`STATE.friendPoints`に加算してから削除します。

## 4. プレイヤーID

- Crockford Base32(`I L O U` を除く)12文字を `XXXX-XXXX-XXXX` で表示します。
- uidからのハッシュで決まるので、**同じアカウントならどの端末でも同じID**になります。
- ログイン時に `playerIds/{code}` を確保します。万一ぶつかった場合は次の候補(`uid#1`, `uid#2` …)に回ります。
- PVP・フレンド機能では、この `code → uid → players/{uid}` の経路で相手を引ける想定です。

## 5. 同期のルール

- セーブは `STATE.savedAt`(**データが変わった時刻**。書き込んだ時刻ではありません)で新旧を判断します。
- ログイン時: クラウドの方が新しければ読み込み、この端末の方が新しければ push します。読み込みで置き換えられた端末のデータは `monster-game-state:<uid>:backup` に残します。
- プレイ中: セーブのたびに8秒のまとめ書きでクラウドに送ります。タブを閉じる・バックグラウンドに回るときは即時に書き出します。
- 書き込みは**条件つき**です(Firestoreのトランザクション)。ほかの端末が後から保存していた場合は上書きせず、`ほかの端末でデータが更新されています` と表示して以降の送信を止めます。読み込み直すと新しい方に揃います。
- オフライン時: ログイン済みならローカルのセーブでそのまま遊べます。復帰後の保存でクラウドに追いつきます。

## 6. ローカル保存のキー

| キー | 内容 |
|---|---|
| `monster-game-account` | ログイン中のアカウント(uid・プレイヤーID・名前・ログイン方法) |
| `monster-game-state:<uid>` | そのアカウントのセーブ |
| `monster-game-state:<uid>:backup` | クラウドで置き換えられた直前のセーブ |
| `monster-game-state` | ログイン導入前のセーブ。最初にログインしたアカウントが引き継ぎます |

`window.storage` が無い環境では `localStorage` を使います(以前は `window.storage` 前提で、**ブラウザでは保存が効いていませんでした**)。

## 7. テスト

本番のFirebaseに接続せずに検証します。

```bash
cd tools
CHROMIUM_PATH=/path/to/chrome python3 auth_test.py
```

- `mock_auth.js` が偽のバックエンド(`window.__authBackend`)で、認証とFirestoreの代わりをします。「クラウド」は `localStorage` に置き、端末Bのシミュレーションではテスト側がその中身を次のブラウザコンテキストへ渡します。
- 確認している範囲: タイトル画面 / ゲスト・メール・Googleの各ログイン / 自動ログイン / ID割り当てとフレンドコード登録 / 公開プロフィール / ゲスト→メールの引き継ぎ / ログアウト / 端末間のデータ引き継ぎ / 新しい方が勝つこと / 接続できないときの表示。
- **Firebase本体のアダプタ(`firebaseBackend`)だけは、この環境から外部に出られないため未実行です。** 実機で最初に確認すべきはここです。
